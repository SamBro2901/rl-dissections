\chapter{Hyperparameters and Configuration}
\label{app:hyperparameters}

This appendix lists the complete parameter sets of the \num{280} canonical runs.
\Zcref{sec:app-hp-baselines} gives the baseline parameters of each algorithm, \zcref{sec:app-hp-protocol} the settings of the measurement protocol that are common to all runs, and \zcref{sec:app-hp-sweeps} the override files that define the sweeps.
\Zcref{sec:app-hp-check} reports the check of the logged configurations against the baselines, and \zcref{sec:app-hp-refit} states how the refit interval of MBPO is evaluated.
The baseline settings and their deviations from the publications are discussed in \zcref{sec:baselines}.
All values were read from the configuration classes (\texttt{configs/config.py}) and checked against the \texttt{algo\_config} and \texttt{experiment\_config} fields of the \texttt{metadata.json} file of every canonical run.

\section{Check of the Logged Configurations}\label{sec:app-hp-check}

The \texttt{metadata.json} file of every canonical run stores the full algorithm configuration and the experiment configuration of the run.
The following checks were run on all \num{280} files.
\begin{itemize}
  \item The logged \texttt{algo\_config} equals the default of the configuration class of the algorithm with the override file of \zcref{tab:app-hp-sweeps} applied, for all \num{280} runs (no deviation).
  \item For each of the \num{56} configurations, the logged \texttt{algo\_config} differs from that of the baseline of the same algorithm and environment in exactly the swept parameter and in no other field (no exception).
        For TD3, the baseline has batch size \num{100}, so the batch-size sweep changes this one field.
  \item Within each configuration, the \texttt{algo\_config} and the \texttt{experiment\_config} are identical for the five seeds, apart from the seed itself and from one logging field described next.
  \item The \texttt{experiment\_config} is identical in all \num{280} runs except for \texttt{warmup\_steps} (\num{10000} in the \num{80} TD3 runs, \num{5000} otherwise).
\end{itemize}
The only exception is a logging field, not a setting: the field \texttt{thermal\_gate\_reference\_file} is stored in the metadata of only three runs (SAC on HalfCheetah-v5, baseline, seeds \num{331}, \num{958} and \num{14577}) and is absent from the other \num{277}, because the runner excludes it from the logged configuration from the fourth canonical run on (\zcref{sec:app-repro-code}).
The thermal gate was enabled and reached its reference state in all \num{280} runs.

\section{Refit Interval of the MBPO Dynamics Model}\label{sec:app-hp-refit}

The configuration field \texttt{model\_train\_freq} is \num{250}, and the training loop of MBPO (\texttt{algorithms/mbpo.py}, function \texttt{train}) refits the ensemble when
\begin{center}
  \footnotesize\texttt{(global\_step - last\_model\_train\_step) >= model\_train\_freq}
\end{center}
holds.
This condition is evaluated once at the start of every epoch of \num{1000} environment steps, and \texttt{last\_model\_train\_step} is initialised to $-250$, so the first epoch also fits.
At every epoch the difference is \num{1000} and therefore at least \num{250}, so the model is refitted at the start of every epoch: \num{100} fits per run, one per \texttt{dynamics\_model\_update} task, and not one fit every \num{250} real steps.
The synthetic rollouts are generated once per epoch as well, directly after the rollout block, so the model buffer is refreshed once per epoch.
The logged number of fit epochs confirms this: in all \num{80} canonical MBPO runs, all \num{100} epochs of \texttt{training\_metrics.json} carry the diagnostics of a fit (\texttt{model\_train\_epochs} is set), i.e.\ there are exactly \num{100} fits per run.
Each fit continues from the weights of the previous one and refits only the input normaliser; the fit stops early after \texttt{model\_train\_patience} epochs without improvement of the holdout error.

\paragraph{Deviation from the publication.} The publication~\cite{janner2019mbpo} lists \num{20} policy updates per environment step on Ant and \num{40} on HalfCheetah, and \num{400} model rollouts per environment step.
The baselines of this thesis use one update per environment step, refit and refill once per epoch, and draw \num{10000} start states for each refill, i.e.\ \num{10} per environment step.
The reasons for this reduction and the resulting limits are given in \zcref{sec:baselines} and \zcref{sec:thr-design}.
